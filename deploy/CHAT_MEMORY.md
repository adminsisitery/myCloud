# 普通聊天记忆链路改造

日期：2026-09-16。适用普通 CHAT 入口；Agent 的规划与执行记忆仍使用现有实现。

## 改动结果

移除“首次提问命中后直接返回旧答案”的分支及 AICacheService。相同问题也重新生成。Redis 改为缓存当前会话的摘要、最近消息和版本；MySQL 保存可回查的原始消息。首个 USER 不再重复加入模型上下文，检索增强内容不再被 JSON 编解码器剥离。

流程：校验用户/模型 → 事务创建或校验会话、获取会话租约、保存原始提问 → 读取版本化记忆缓存（未命中或异常时回源 MySQL）→ 检查 20 轮与 token 阈值 → 必要时整理旧摘要和较早记录 → 组装摘要、最近记录、当前问题、检索片段 → 模型回答或调用历史回查工具 → 事务保存成功回复、工具轨迹、用量并释放租约 → 更新缓存 → 发送 done。

## 三层记忆

| 层次 | 实现 | 约束 |
| --- | --- | --- |
| 原始记录 | `t_ai_message`，用户提问和成功的助手回复 | 窗口裁剪、摘要和缓存过期均不删除；只有显式删除会话时删除 |
| 摘要与状态 | `t_ai_chat_memory` | 五类结构化摘要、原文消息 ID、摘要游标、版本、历史缺口标记、会话租约 |
| 短期缓存 | Redis `ai:memory:v1:{user}:{conversation}:{version}` | 默认 30 分钟过期；内容为 JSON 中的 List 和摘要，不是旧答案缓存；数据库状态决定有效版本 |

默认把 20 轮作为上限阈值，一轮按 USER 起始及其后回复划分，而非把工具消息算作一轮。新请求开始时，若已有 20 轮，则压缩较早 10 轮、保留最近 10 轮；短期内容估算超过 8,000 token 时提前压缩。失败请求保留 USER 原文，但不会伪造成功回复。当前一轮的工具请求和工具结果不在执行途中裁剪。

摘要包含 goals、constraints、facts、decisions、openQuestions。每项带 speaker 和 sourceMessageIds。写入前校验 JSON、长度、非空内容和引用 ID；空摘要、虚构 ID、截断输出或生成失败均不会推进摘要游标。本轮返回错误，原文保留。结构校验不能证明摘要语义完全准确，关键数字和约束仍需回查原文。

## 历史主动回查

- 命中“之前、刚才、上次、前文”等指代时，服务端先回查当前会话最近 4 条原文。这只是一种提示性检索，不保证命中远期内容。
- 模型可调用 `searchConversationHistory(keyword,beforeMessageId)`：参数化关键词查询、向前分页、最多 4 条，每条最多 1,200 字符。
- 模型可调用 `readConversationMessages(messageId,offset)`：每页最多 2,000 字符，读取摘要引用的原始记录。
- 自动回查与工具回查共用每轮默认 3 次额度；用户 ID、会话 ID由服务端绑定，模型不能传 SQL 或切换用户/会话。
- 未命中、无法检索或额度耗尽时，提示模型说明缺少的信息并让用户补充。不能保证模型总会正确识别“自己缺少记忆”。

## 正确性与异常行为

- **缓存异常**：读取损坏、过期、版本/游标不匹配或 Redis 失败时回源数据库。缓存写入失败不回滚已完成的聊天。旧版本的迟到写入不会覆盖新版本。
- **并发请求**：数据库会话锁和带截止时间的租约串行化同一会话；跨实例也适用。并发提交返回 409。过期租约可接管，旧回调不能释放新租约或补写成功回复。
- **重复提交**：`requestId` 在用户范围内唯一；重复提交返回 409，不重新执行。不传该字段则每次视为新请求。新会话创建和首次 USER 入库在同一事务内。
- **流式结束**：仅完整回复才写入 ASSISTANT、增加成功轮数并发送 done。模型错误、输出截断和超时记录 FAILED；进程失联后遗留 RUNNING 在下一次接管时转为 TIMED_OUT。
- **token 记账**：成功、摘要和已知失败调用分别记录 `chat`、`chat_summary`、`chat_failed`。每个模型工具续轮均经过上下文预算检查；已开始但没有返回 usage 的供应商请求不能精确记账。
- **RAG 证据**：当前增强消息保留到真实模型请求；原始 USER 表中保持用户原话。聊天入口核验文件现存所有权与删除状态，最多 5 段，每段最多 1,200 字符，文字中明确附带真实文件 ID。不会声称片段等于全文。ES 异常时尝试向量检索，均失败则明确给出不可核实状态。
- **工具轨迹**：当前增强用户消息、工具请求和结果保存到 `t_ai_chat_turn.messages`，与前端原始聊天记录分开。工具完成时更新检查点，终态再次保存。崩溃发生在检查点前时，未落库的工具轨迹可能缺失。
- **取消/断连**：本地终止后禁止后续模型轮次、历史查询和成功落库；SDK 已经发出的远端请求不保证能立即取消。
- **删除会话**：有有效聊天租约时拒绝删除；完成后删除会话同时清理新记忆/轮次表。Redis 旧 key 自然过期，所有权校验阻止继续访问已删会话。

## 部署与旧数据

1. 先备份现有数据库，并确认已完成 `001-agent.sql` 的表结构升级。
2. 在目标 MySQL 8 数据库执行同目录的 `003-chat-memory.sql`。这是新增两张表的幂等脚本，不清理原始历史。
3. 发布新后端并重启。`agentSchema` 健康检查会检查新增记忆表；缺少迁移时 readiness 不通过。
4. 按 `application-template.yml` 中的 `ai.chat-memory` 配置阈值。`context-token-budget` 必须小于实际启用模型的上下文窗口并预留余量。现有 tokenizer 是近似估算，不是所有模型的精确计数器。
5. 验证聊天、超过 20 轮、Redis 缓存失效、数据库回查、并发 409 和中断重试。上线前还应使用实际模型评估中文约束保留与长期记忆命中率。

本次没有执行生产数据库迁移、重启服务或调用真实付费模型。

旧的 `memory_state` 不再作为新链路的事实来源。已有很长的会话只读取有界近期记录，标记未覆盖的远期历史，并可通过工具查原文；不会自动把整个旧会话全部重放给模型。旧逻辑已经物理删除的历史无法由这次改造恢复，需要旧备份。

压缩最多调用模型 8 次，并受会话租约和摘要长度上限约束。极长旧记录可能触及整理上限；此时保留原文并拒绝继续本轮，可新建会话、缩小待处理范围或由管理员调整策略。不能把反复重试理解为一定会恢复。

回滚时可保留新增表，不应删除用户历史。旧版本的 DbChatMemoryStore 存在裁剪删除历史的缺陷，不建议直接回退到该实现。

## 本次范围之外

此次改造降低记忆丢失和证据缺失的风险，不能消除模型幻觉。Agent 的规划历史、结果证据校验、48k 字符预算与普通聊天前端 SSE 解析等问题仍按原审计报告处理。
